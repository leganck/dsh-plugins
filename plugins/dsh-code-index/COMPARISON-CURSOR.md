## 一、先讲清一个前提：两者形态不同的根源

Cursor 的索引跑在**服务端**（本机 `~/.cursor` 下没有任何索引文件——实测确认）。
所以它那套 Merkle 同步协议、路径加密（`pathEncryptionScheme` + `orthogonalTransformSeed`）、
上传限流（`GetUploadLimits{soft,hard}`）、simhash 索引复用，**是多租户云产品逼出来的**，
不是算法本身的必需品。本插件是**本地进程**，这些层可以直接不存在。

**真正值得对齐的只有四层：切块、缓存键、增量、查询排序。**

## 二、逐层对照

| 层 | Cursor | code-index（本插件） | 差距评价 |
|---|---|---|---|
| **新鲜度/同步** | Merkle 树：文件哈希 + **目录聚合哈希**；握手只发 `root_hash`；`SyncMerkleSubtreeV2` 只走哈希不同的分支；`max_sync_merkle_batch_size` 分批 | `files(path, mtime, size, sha256)` 表 + 全量 `walkRepo` + `diffFiles`（mtime+size 快筛，内容 sha256 定稿）。**实测**：遍历 120 ms / 2,088 文件；全量核对 703 ms；未变时 ~2 ms | **不需要对齐**。Merkle 省的是**网络传输**；本地遍历已经在毫秒级，2 ms 与"剪枝"无差别 |
| **切块** | **AST/语法切块**：客户端原生模块 `@anysphere/tree-chunk-napi`（tree-sitter），服务端可下发策略 `GetAvailableChunkingStrategies`；块带 `language_identifier` / `summarization_strategy` / `intent` / **`is_first_version`、`is_final_version`**（草稿→定稿生命周期） | ✅ **已落地**：`lib/chunk-ast.js`（tree-sitter）+ `lib/chunk-heuristic.js`（纯 JS 兜底）+ `lib/strategies.js`（**策略表**，对应 `GetAvailableChunkingStrategies`：按扩展名查表 + 配置覆盖 + 依赖缺失自动降级）。块哈希 = `sha256(完整块文本)` | ✅ **质量差距已基本闭合**（见第三节实测）。不做 `is_first_version/is_final_version`——那是服务端增量同步的状态机，本地重建一次只要秒级 |
| **原生依赖的获取** | 随客户端分发（用户无感） | **按需安装**：`parser` 组 5 个包 60.3 MB（实测 2 秒，全部走预构建、零依赖脚本），缺则自动降级并**如实报告原因** | 设计取舍：本地无分发渠道，所以把"装插件"与"装依赖"解耦（见第七节） |
| **内容缓存** | 向量按**块内容哈希**缓存；"大多数编辑不改动大多数块 → 命中缓存" | 全局**内容寻址**缓存 `~/.dsh/index/vectors.db → vec(key, dim, v)`，`key = ${模型标签}:sha256(送模型的文本)`；**跨仓库、跨版本共用** | ✅ **同构，而且我们的更细**（逐块精确复用 vs 服务端按仓库组织）；AST 落地后改动文件内的复用率**翻倍**（第三节） |
| **关键词通道** | `BM25Chunk { content, range, score, relative_path }` | FTS5（`chunks_fts`，unicode61）+ `bm25()` 排序 | ✅ 同构（FTS5 的底层就是 BM25） |
| **向量通道** | 自研 embedding（训练数据来自 agent 会话轨迹） | 可选：bge-small-zh-v1.5（fp16/DirectML 或 int8/CPU），512 维，L2 归一化 | 模型档次不同，接口同构 |
| **融合与重排** | 向量 kNN + BM25 → **`use_reranker` 重排**；两档延迟入口 `SemSearch` / `SemSearchFast`；请求带 `CurrentFileInfo{contents, sha_256_hash, top_chunks}` | BM25 + kNN → **RRF(k=20) 融合**；**无重排** | ⚠️ 有差距但**不是下一步**：103 题实测重排值 **+19.4pt**（hit@3），代价却是**每查询 +5 s** ✗ → 同样 +19pt 换 bge-base 只需一次性成本。见 **5.7.3** |
| **请求上下文** | 搜索请求自带当前文件内容 + 其 sha256 + top_chunks | 无（`code_search` 只接查询串与仓库路径） | 中等：缺"以当前文件为锚"的检索 |
| **目录地图** | `GetHighLevelFolderDescription`（目录级摘要） | 无 | 中等：冷启动时不知道去哪儿找 |
| **变更流程** | watcher 只标记 → 周期 `doUpdate`（`indexing_period_seconds` **≥60 s**，且有自我抑制：有 job 在跑或处于超时窗口就跳过本轮）→ 子树剪枝 → `FastUpdateFileV2{MODIFY, ancestor_spline}` → spline 不一致得 **`EXPECTED_FAILURE` → 重同步该子树（不是重试）** → 重新分块 → 未变块命中缓存 → **只嵌入变化的块**（后台异步） | 按需触发建库/刷新，无后台周期；改文件 → **整文件**重新切块并重写 chunks + FTS；向量层因缓存内容寻址，未变的块**自然命中** | ✅ 语义接近。切块边界现在也稳了（AST），所以"未变块命中缓存"这条真正生效 |
| **删除** | `deleteFastUpdateFileWithRetry{DELETE}`（并发 10，超额 `setTimeout(300)` 让拍）；整库 `RemoveRepositoryV2` | `dropFile(rel)` 一次事务删 chunks / FTS / `vectors` | ✅ 等价（本地无需祖先证明与并发限流） |
| **状态机** | `RepositoryCodebaseInfo.status ∈ {UP_TO_DATE, OUT_OF_SYNC, EMPTY, EMPTY_WITH_COPY_AVAILABLE, COPY_IN_PROGRESS}` | `code_index_status` 报 changed / unchanged / removed / stale + 块数与向量数；另有**切块策略指纹**（换了策略自动全量重建，避免库里混两种粒度） | 我们的更简单，本地单实例够用 |
| **冷启动复用** | **simhash**：把整棵树哈希压成一个值 → 服务端在团队已有索引里检索相似度 → **整份索引复用**（"小时级→秒级"） | 无"整份复用"；但**逐块复用已覆盖大部分收益**——仓库级块重合 **~98%**，改动文件内 AST 复用 **29%–38%**（第三节） | ⚠️ 优先级低（论证见第四节） |
| **索引位置** | 服务端（本地无索引文件） | `~/.dsh/code-index/<仓库名>-<路径哈希前8>/index.db`，**不落在代码仓库里**（不污染 `git status`） | ✅ 本地化后天然更好 |

## 三、切块：**当前口径的实测**（真值来自语法树）

### 3.1 指标定义与一次指标纠错

**"块首行/末行落在成员内部"** = 块从方法/字段**中间**开始或结束，也就是"半截成员"。
真值 = 语法树里成员级节点（方法/构造器/字段/内部类）的行跨度，用 tree-sitter 直接算。

> ⚠️ 早前用过"块内大括号是否平衡"当质量指标，**那个指标是错的**：AST 切出的块是
> "类里的一个方法"，天然不包含类的那个 `{`，于是整块计数**必然不为 0**——
> 它把正确切法判成异常（AST 66.8% 反而"差于"启发式 52.8%）。已弃用，不要再用。

### 3.2 三种切块器横向对比

| 仓库 | `window`（固定 40 行） | `heuristic`（纯 JS） | **`ast`（tree-sitter）** |
|---|---|---|---|
| `saas`（8,777 个 Java 文件）<br>块数 / 平均行 / **首行落成员内** | 22,619 / 33.3 / **29.4%** | 18,765 / 40.1 / **7.5%** | 17,206 / **33.8** / **0.1%**（30 个超长成员被强制拆分） |
| `legacy-java-service`（94 个 Java） | 207 / 32.3 / **15.0%** | 179 / 37.4 / **6.1%** | 152 / **34.2** / **0.0%** |
| `legacy-java-service`（**144 个 Groovy**，Grails） | —（本轮未测） | 506 / 49.5 / **31.6%**（160/506） | 436 / 53.1 / **6.7%**（maxLines 200；非强制块 **0.7%**，3/403） |

**最值得注意的一格**：AST 的**平均块尺寸与固定窗口几乎相同**（33.8 vs 33.3、34.2 vs 32.3），
但"首行落在成员内"从 29.4% / 15.0% 降到 0.1% / 0.0%。
也就是说**收益来自对齐，不是来自"块变大"** —— 这条排除了"你是不是靠放大块来刷指标"的质疑。
（早期 AST 实现因为漏了尺寸上限，平均是 45.1 行；补齐上限后回到 33.8，对齐质量不变。）

**由 Groovy 那一行得到的通用性质**：AST 的**非强制块几乎完全对齐成员边界**
（Groovy 0.7%、Java 0.1%），残差**主要**来自"成员本身比 `maxLines` 长"。
所以长成员语言的正确做法是**调大该语言的 `maxLines`**，而不是接受半截块——
策略表里 `.groovy`/`.gradle` 因此设为 200（强制拆分从 56 降到 33，残差 10.5% → 6.7%）。

### 3.3 真实索引重建后的块尺寸（新加的不变量）

| 仓库 | 块数 | 平均 | 中位 | p90 | **最大** | >120 行 |
|---|---|---|---|---|---|---|
| `legacy-java-service`（280 文件） | 675 | 47.7 | 42 | 71 | **200** | 32 (4.7%) |
| `legacy-grails-service-5.0`（1,308 文件） | 4,491 | 64.4 | 48 | 120 | **200** | 94 (2.1%) |
| `sql`（58 文件，`.sql` → window） | 167 | 47.5 | 60 | 60 | **60** | 0 |

> 这条不变量是**踩坑后补的**：早期 AST 打包只在"够到 targetLines"时收口，
> 短单元并入那条分支没查上限 → 实测跑出 **1,214 行的块**（上限本应 120）。
> 而"首行是否对齐"那种指标**只看起头、看不到结尾**，抓不到它。
> 另修一处：库里没有指纹记录（= 指纹机制之前建的索引）时曾被判成"没变化"，
> 导致迁移时只重切了 14 个文件、库里混着两种粒度的块。

### 3.4 跨版本块复用率（改动文件内，两种切法都走**产品代码路径**）

| 场景 | 内容有差异的文件 | 固定 40 行窗口 | **AST** |
|---|---|---|---|
| 同分支差 20 提交 | 13 | 3.3% | **29.2%** |
| `5.0` ↔ `feat/plat/3.45.0` | 131 | 17.5% | **35.7%** |
| `5.0` ↔ `master` | 128 | 16.6% | **35.1%** |
| `5.0` ↔ `your-org/3.35`（大分歧） | 162 | 12.0% | **37.8%** |

**读法**：改动一个文件后，固定窗口下该文件里 **82.5%–96.7%** 的块哈希都变了（插入一行会平移后面所有窗口）
→ 这些块必须重新嵌入；AST 只让 **62.2%–70.8%** 的块需要重算，**复用率约翻倍**。

把"内容逐字节相同的文件"算进来后，**仓库层面复用三种场景都是 ~98%**（一次分歧通常只动几十到一百多个文件）
—— 所以：**跨分支共享**场景下固定窗口已经够用；**单仓库内反复编辑**（活跃开发）
才是切块边界真正省算力的地方，AST 在这里的收益是翻倍级的。

## 四、不要照抄的两处（当时就说了，现在有数据支撑）

1. **Merkle 同步协议**：它省的是网络传输。本地全量核对 703 ms（2,088 文件），
   未变时 2 ms —— 加一层目录聚合哈希换不来可感知的收益，却引入"树不一致怎么办"的复杂度
   （Cursor 自己都要处理 `EXPECTED_FAILURE` 与 `hackyGetSplineWhenYouCantRelyOnTree` 兜底）。
2. **simhash 整份索引复用**：对"一个仓库五个版本"的收益，**我们的逐块内容寻址已经拿到大半**——
   仓库级复用 ~98%，且 AST 之后改动文件内也有 29%–38%。整份复用的额外收益很小，
   而代价是"整份索引复制的正确性"（状态机 `EMPTY_WITH_COPY_AVAILABLE` / `COPY_IN_PROGRESS` 就是在处理这个）。

## 五、融合 vs 重排：作用分析（**结论以 5.7.3 为准**）

> 本节 5.1–5.6 是**分析与推算**（当时还没有题库）；5.7 是用 **103 题实测**出来的结果。
> 若二者冲突，**以 5.7.3 为准** —— 实测把"重排净负"翻成了"重排 +19.4pt，但每查询 +5 s 太贵"。

### 5.1 先把两者分清楚

| | 融合（我们已做） | 重排（我们没做） |
|---|---|---|
| 输入 | 多条召回通道的**名次** | 一批**已召回的候选** |
| 做法 | `score = Σ 1/(k + rank_i)`，`k=20` —— **纯算术，不是模型** | 交叉编码器：query 与 doc **拼在一起**过一次模型 |
| 能否预先算 | 能（只依赖已有名次） | **不能**，只能在线对小集合跑 |
| 作用在哪个指标 | **recall**（正确答案在不在候选集合里） | **precision@10**（正确答案排不排进前 10） |

**关键约束**：重排**只能在已召回的集合内重排** → **它的性能上限 = recall@K**（K = 候选数）。
答案不在候选里，重排救不了。

**顺带复核 Cursor 侧这两步在哪儿做**（2026-10-16 从已发布客户端 bundle
`extensions/cursor-retrieval/dist/main.js` 的 protobuf 定义读出，非运行时观测）：

```js
semSearchFast: {name:"SemSearchFast", kind: Do.ServerStreaming},
semSearch:     {name:"SemSearch",     kind: Do.ServerStreaming},   // 同一对请求/响应类型

aiserver.v1.RerankerAlgorithm:
  1 LULEA  2 UMEA  3 NONE  4 LLAMA  5 STARCODER_V1  6 GPT_3_5_LOGPROBS
  7 LULEA_HAIKU  8 COHERE  9 VOYAGE  10 VOYAGE_EMBEDS  11 IDENTITY  12 ADA_EMBEDS

aiserver.v1.SemSearchResponse.SemSearchMetadata: { query_embedding_model, …, knn_latency_ms }
aiserver.v1.RerankDocumentsRequest { query, documents[] }  →  RerankDocumentsResponse
aiserver.v1.ContextRerankingCandidateFile{file_name, file_content} → ContextRankedFile{reranking_score}
```

结论：**融合与重排都是"服务端 + 在线（查询期）"**，证据是——
① 检索本身是**服务端流式 RPC**（客户端不持有索引，只有 Merkle 树）；
② 重排算法枚举里含 **Cohere / Voyage**（托管 API）与 **GPT_3_5_LOGPROBS / LLAMA / LULEA_HAIKU**（LLM 打分），
这些**只能在线调用、不可能离线预计算**；
③ 服务端把 `knn_latency_ms`、`query_embedding_model` **回报给客户端**，说明查询嵌入 + kNN 每次现算；
④ `NONE` / `IDENTITY` 这类"不重排"的枚举值 + 两档入口，说明重排是**查询期可开关**的一步。
离线（索引期）只有：切块 → 块嵌入（只算变化块）→ BM25 倒排 → Merkle 同步。

### 5.2 融合：实测价值与代价

| 通道 | hit@10（本机 40 个真实检索事件） |
|---|---|
| 纯 FTS5（BM25） | 32.5% |
| 纯向量 kNN | 37.5% |
| **RRF 融合** | **55%** |

融合的收益是**互补**而非平均：32.5 + 37.5 远小于 55，说明两路命中集合重叠不多。
RRF 的代价是**丢掉"这一条有多强"**（第 1 名相似度 0.99 与 0.51 被同等对待）——
换来的是**免归一化**（BM25 无上界、余弦有界，量纲不可比）。
本插件返回里带 `ftsRank`/`vecRank`/`score`，可以手工验算 `score ?= 1/(20+ftsRank) + 1/(20+vecRank)`。

### 5.3 一个**自我设限**的发现

`lib/search.js` 现在：`RRF_K = 20`、`FTS_CANDIDATES = 40`、`VEC_CANDIDATES = 40`。
也就是说候选池最多 80 条，融合后取 topK。
**抬高这两个上限几乎零成本**（kNN 是对 8k 向量的点积、FTS5 只是 `LIMIT`），
却能直接抬高重排的天花板 —— 在装重排器之前应该先把这一步做掉，否则量出来的
"重排没效果"可能是被自己的候选上限卡住的。
（**5.6 补充了前提**：这个"几乎零成本"只在**不重排**时成立。）

### 5.4 顺带澄清：喂给模型的**不是整块**

`code_search` 每条结果 = `path` + `startLine/endLine`（坐标）+ 两条通道各自的名次 +
`snippet`（命中词附近**最多 8 行、截到 320 字符**）。
所以：**块是"检索的匹配单元"和"缓存复用单元"，不是"给模型看的单元"**；
模型主要靠坐标去读文件。这也意味着**块边界质量主要影响检索匹配，不主要影响模型看到的文本**。

### 5.5 延迟实测：查询嵌入 vs 重排（本机、真实模型）

环境：win32-x64、`bge-small-zh-v1.5` fp16 / **DirectML**、已装依赖，逐项实测：

| 项 | 实测 |
|---|---|
| 冷启动（ONNX 会话初始化 + 首次前向） | **96 ms**（一次性） |
| **查询嵌入**（12 字符，8 个不同查询） | **中位 27.8 ms**（min 24.3 / max 83.3） |
| 单个完整块（1500 字符 ≈ 500+ token） | 中位 **48.0 ms** |
| 批量 20 个长文本 | 1452 ms → **72.6 ms/条** |
| 批量 50 个长文本 | 2353 ms → **47.1 ms/条**（21 条/s） |

**发现①：查询嵌入不是按 token 线性，而是固定开销主导。**
12 字符 27.8 ms、1500 字符 48.0 ms —— 序列长 100 倍只慢 1.7 倍，约 **25 ms 是每次前向的固定成本**。
含义：查询嵌入**不可能靠"查询短"变便宜**（30 ms 是地板），也**不会因为查询变长而明显变慢**。

**发现②：在这个后端上批量不划算。** 批量 20 是 72.6 ms/条，比单条 48 ms **更慢**——
与 `lib/embedder.js` 里记录的"DirectML 在 batch 8–16 最快、32 会掉下来"一致。
所以"重排靠批处理摊销"这个直觉**在本机不成立**。

**量级结论**：查询嵌入 = **1 次前向、与候选数无关、相同查询还命中缓存**（第二次近免费）
→ **要求不高，每次检索固定 ~30 ms，不需要优化**。
重排 = **N 次长前向，N = 候选数** → **数量级差异**：

| 重排候选数 | 额外耗时（按单条 48 ms） |
|---|---|
| 10 | ~0.5 s |
| 20 | **~1.0 s**（本机批量实测 1.45 s） |
| 50 | **~2.4 s**（实测） |

即：**一次检索会从 ~30 ms 变成 1–3 秒，与候选数线性相关**。而交叉编码器通常比嵌入模型更大
（本插件模型 24 M/6 层；`bge-reranker-base` 级别约 110 M/12 层 ≈ 4–5 倍）→ 每候选可能 200 ms+，
20 个候选就是 4–5 秒。**所以真要做必须选小交叉编码器（MiniLM-L6 级）或 int8 + 限制 maxlen（256 而非 512）。**

> ⚠️ **量测方法本身也踩过一次坑**（留档）：第一版量测里"单条 0.2 ms"是错的——
> 同一段文本第二次调用直接命中**内容寻址缓存**，于是把"缓存命中"量成了"前向耗时"。
> 可信口径必须是：**每次换文本**，或干脆看批量吞吐。

**这解释了 Cursor 的设计**：`SemSearch` / `SemSearchFast` 两档 + `RerankerAlgorithm` 里的
`NONE`/`IDENTITY` —— 正因为在线重排贵，必须给调用方一个"要不要为排序质量付 1 秒"的开关。

### 5.6 由此修正 5.3 的结论

候选上限该怎么抬，取决于**有没有开重排**：

| 情况 | 候选上限 40 → 200 的代价 |
|---|---|
| **不重排**（现状） | **几乎为零**（只多花 kNN 点积与 FTS5 `LIMIT`，微秒到毫秒级）→ **应该先做** |
| **开启重排** | 候选数会变成**延迟乘数**（20 → +1 s、50 → +2.4 s）→ 重排只能吃 **top-15~30**，不能吃整个候选池 |

所以正确顺序是：**先抬上限（零成本，同时抬高召回）→ 测 recall@K → 若上重排，则重排候选数与召回候选数分开配置**，
并且重排**默认关**（学 Cursor 的快档/慢档），需要精排时显式开。

#### 5.7.3 修正后的结论

1. **"重排净负"是 4 题样本的假象** ✗ —— 同一个题库在 4 / 20 / 103 题上给出过三次互相矛盾的结论，

2. **重排的收益与"换 bge-base"几乎相同**（都是 hit@3 **+19 pt** 左右），但**代价形态不同**：

   （全量 6.7 万块 = 20.0 M tokens ≈ **$0.24**），而每次 +5 秒没法摊 ✓

## 七、tree-sitter 落地的记录与三个坑

结论：**已落地并在真实仓库跑通**（Java / JavaScript / TypeScript+TSX / Groovy，原生非 WASM）。

| 项 | 实测值 |
|---|---|
| 解析吞吐 | **2,235 文件/秒、6.7 MB/秒**（342 个 Java 文件 153 ms） |
| 端到端（含读盘） | 342 文件 **392 ms** |
| 解析失败 | **0/342**（修掉 `bufferSize` 之后） |
| 依赖体积 | `parser` 组 5 个包 **60.3 MB**（预构建齐全，装 2 秒、零依赖脚本） |

**三个坑（按"难查程度"排序）**：

1. **`setLanguage` 必须传语法包的"元数据对象"，不能传它的 `.language` 子对象。**
   tree-sitter 把参数原样存成 `tree.language`，之后 `unmarshalNode()` 读它的
   `nodeSubclasses`（由语法包的 `nodeTypeInfo` 派生）。传 `.language` 的症状是——
   **`setLanguage` 不报错、`parse` 也不报错，直到读取节点才抛**
   `Cannot read properties of undefined (reading '138')`（数字是节点类型 id），
   而栈顶指向 tree-sitter 内部 `index.js:771`，与调用点无关。
2. **版本配对是硬约束。** `tree-sitter-java@0.23.5` 声明 `peerOptional tree-sitter@^0.21.1`，
   但预构建与 0.21.1 不兼容（0.25.1 也崩、0.22.4 ERESOLVE 装不上）。
   最终可用组合 = **同年代配对**：运行时 `tree-sitter@0.21.1` + java `0.21.0` /
   javascript `0.21.4` / typescript `0.21.2` / groovy `0.1.2`。
   **改版本时四个包必须一起实际解析一次**——只有解析能证明配对成立。
3. **`bufferSize` 必须显式传**：JS 包装默认 **32 KB**，字符串输入超过就抛 `Invalid argument`
   （二分实测 32,767 通过 / 32,768 失败）。只在**大文件**上暴露：小仓库全过、大仓库第一个大文件就崩。
   统一传 `Math.max(text.length, Buffer.byteLength(text,'utf8')) + 4096`。

**依赖按需安装**（第七节的一半价值在这里）：这两个原生依赖组都**不写进 package.json**，
装插件只装纯 JS 部分（tarball ~70 KB，实测 `Done in 876ms`、`pendingBuilds` 无此键、零审批）；
需要时 `code_index_deps action=install group=parser|embed` 下到自管目录
（`%LOCALAPPDATA%\dsh-code-index\embed-deps`，与插件安装解耦，重装插件不重下）。
早期把依赖写进 `optionalDependencies` 时踩过三件事：装插件要下 463 MB、pnpm/npm 都拦依赖脚本要人类批准、
最坏撞上服务侧 600 秒空闲超时导致整次安装回滚。

4. **`is_first_version` / `is_final_version`（草稿→定稿）** —— 不做。那是服务端增量状态机的产物，本地重建只要秒级。
5. **Merkle / simhash** —— 0.12 起 simhash 只做候选发现，不做整库 copy（见第十二节）。

### 这轮抓到的两个"行为不对齐"的真问题

1. **切块能力没进指纹**（0.8.2 修）：装 tree-sitter 前后块边界变了但指纹不变 → 同一命名空间混两种粒度。
   现在指纹 = 配置 + 本仓库实际用到的可用语法；且换命名空间不等于重嵌（内容哈希在血统内去重，
   energy 实测 1501 块只有 5 块需要重算）。
2. **嵌入队列 FIFO 饿死小仓库**（0.8.2 修）：服务端原来把队首命名空间排干再换下一个。
   实测在 43,836 待嵌的大仓后面新建小仓库 → **181 s 后覆盖率仍是 0%**（新增代码在语义通道上搜不到）。
   改成**每批轮转**后：同一个仓库 **18.5 s 到 100%**。

## 十二、0.12 后续对齐（扫描边界 / 自动 freshness / simhash adopt）

> 计划全文见 [`docs/code-index-cursor-alignment-plan.md`](../../docs/code-index-cursor-alignment-plan.md)。

### 12.1 扫描边界

- 新增 `.gitignore` / `.cursorignore` / `.cursorindexingignore` 解析；默认支持嵌套 `.gitignore`；
- `.md` 默认索引，Office/PDF 不在 include；二进制伪装文件被嗅探跳过；
- 明确**不解析构建系统**：business 5.0 中未启用的 Groovy 模块默认仍会索引，必须通过 ignore 或 `exclude` 排除；
- `code_index_status` 报告 ignored 数量与来源。

### 12.2 自动 freshness

- `sync.watch` 默认打开，只监听已建过索引的仓库；
- 持久 registry（`<DSH_HOME>/code-index/repos.json`）支持 DSH 重启后恢复；
- 修复运行中丢事件：dirty 标记 + maxDelay；
- 5 分钟 `scanStatus` 对账兜底；
- 仓库级锁避免多 DSH 进程重复同步。

### 12.3 simhash 复用

Cursor 的机制（[官方博客](https://cursor.com/blog/secure-codebase-indexing)）是：

```text
Merkle tree → simhash → 服务端向量库找同团队近似 index
→ 复制整份 index → content proof 过滤本地没有的文件
```

我们的实现**只借候选发现**：

```text
文件 manifest → path/content 两个 simhash
→ 服务端 Hamming 候选 → 目标 chunks ∩ 候选 vectors 精确重叠
→ 只复制目标确实拥有的 blobs/vectors
```

不复制候选 chunks/path，不做整份 index copy；同一 remote 仍按 lineage 自动共享。`remote.reuse` 默认 `suggest`，验证后可按团队策略切 `auto`。
