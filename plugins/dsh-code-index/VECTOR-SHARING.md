# 向量共享：可行性分析（含实测数据）

> 问题：公司内部多人在**同一个仓库的不同分支**上工作，能否共享 code-index 的向量，
> 让后来者不必重算？
>
> 结论：**能。当前架构已经"半只脚"在里面**（缓存是内容寻址的），
> 但**必须先做 CDC 分块**，否则共享几乎白做 —— 实测只能省掉一半的算力。

---

## 一、为什么天然可共享：缓存是内容寻址的

`lib/embedder.js:34-36`：

```js
static keyOf(tag, text) {
  return `${tag}:${sha256(text)}`          // 键 = 模型标签 + 内容哈希
}
// 表结构：create table vec (key text primary key, dim integer, v blob)
```

由这一点直接得到四条性质：

- **键与路径、行号、分支、机器全部无关** → 两台机器的同一条键必然同义，可直接合并。
- **缓存不存原文**（只有 `key / dim / v`）→ 共享它不直接泄露源码（但有下面的字典确认问题）。
- **向量已 L2 归一化**（`l2()`）→ 合并后可直接用于点积检索。
- **重复内容自动塌缩** → 这是共享能省算力的根本机制。

实测该缓存现状（2026-10-16）：

| 项 | 值 |
|---|---|
| 条目数 | **62,479**（`bge-small-zh-v1.5-fp16` 62,476 + `…-int8` 3） |
| 单条 | dim=512，float32 → 裸向量 **2,048 字节** |
| 裸向量合计 | 122.0 MB |
| 文件大小 | **251.2 MB**（4,096 B × 64,309 页）→ **≈ 4.2 KB/条**（含键索引与页开销） |
| 键长度 | 平均 87 字符（`bge-small-zh-v1.5-fp16:` 24 + 64 位十六进制） |

**注意这个对比**：单个仓库只有 1,022 块（svc-center）与 8,227 块（saas-business），
而缓存里已经有 62,479 条 —— 说明它**早就在跨仓库、跨版本累积**，重复内容已在塌缩。
共享要做的是把这个性质从"单机内"扩展到"公司内"，而不是发明新机制。

## 二、什么能共享、什么不能（最关键的切分）

| 产物 | 能否共享 | 原因 |
|---|---|---|
| 全局 `~/.dsh/index/vectors.db` → `vec(key, dim, v)` | ✅ **就传它** | 键是内容哈希，与分支无关 |
| 每仓库 `<indexDirBase>/<slug>/index.db` | ❌ **不能** | 含 `chunks(path, start_line, end_line, body)` 与 FTS5 的**原文**，全是分支相关的 |
| `index.db` 里的 `vectors(chunk_id, dim, v)` | ❌ | 以**局部 rowid** 为键，跨机器无意义 |

**正确形态**：共享"内容 → 向量"这一层；**结构索引（路径/行号/FTS）各自本地重建**，
重建后再从共享缓存命中向量。重建本身很便宜（FTS5 建库亚秒级）。

一个实现上的小前提：本地 `chunks.hash` 是 **完整 body** 的 sha256，而缓存键用的是
`bodyForEmbedding(body)`（**截断到 1500 字符**，见 `lib/indexer.js:106` 与 `lib/chunker.js:45-47`）——
超长块的这两者不相等。共享前要统一成一个规范键。

## 三、切块边界：**不是**共享的前提条件（此处修正过一版）

现状（`lib/chunker.js:27-42`）是 **40 行固定窗口**，块哈希 = `sha256(40 行文本)`。
文件中间插一行 → 该行之后所有窗口的文本都变 → 哈希全变。

**但"这会不会毁掉共享"取决于场景**。2026-10-16 用 git 两版本对比实测
（仓库 `legacy-grails-service-5.0`，见 `dsh-comparison/overlap-revs.mjs`）：

| 场景 | 差异文件数 | 固定窗口在**差异文件内**的命中率 | CDC |
|---|---|---|---|
| 同分支差 20 提交 | 10 | 9.1% | 45.2% |
| 5.0 ↔ feat/plat/3.45.0 | 36 | 26.0% | 75.6% |
| 5.0 ↔ master | 35 | 26.4% | 76.2% |
| 5.0 ↔ your-org/3.35（大分歧） | 30 | 15.8% | 64.5% |

关键在**把"内容完全相同的文件"一起算进来之后**：一次分支分歧通常只动几十个文件，
所以**整个仓库层面的复用率在三种场景下都是 ~98%，两种切块器差别很小**。

**修正结论**：

- **对"跨分支共享"这件事，CDC 不是前提** —— 现状的固定窗口已经能复用 ~98%，先做共享是划算的。
- CDC 真正省的是**同一文件被反复编辑**时（活跃开发）的重复嵌入：差异文件内部要重算的块
  从 74–91% 降到 24–55%，即 **2–3 倍**。
- （本节早前引用过一组"固定窗口 53.6% / CDC 98.7%"的数字，来自更早的会话记录；
  本轮用上述口径**无法复现**，因此已删除，不作为结论依据。）

## 四、必须一并修的三处（否则共享会把问题放大到全组）

1. ~~**标签要并入模型文件哈希**~~ ✅ **0.4.6 已修**
   现在 `modelTag = bge-small-zh-v1.5-<sha8>-<fp16|int8>`，其中 `sha8` =
   `sha256(model_*.onnx + tokenizer.json + tokenizer_config.json)` 的前 8 位
   （三者一起算，因为**换分词器同样会改变向量**；进程内记忆化，实测读一次 45 MB 花 114 ms）。
   实测值：`model_fp16.onnx` 那一组 → `…-716c6e6f-fp16`；`model_int8.onnx` → `…-ae28901b-int8`。
   （早前本节记录的单文件哈希 `60d0fe5e…`/`b9837c19…`/`48cea5d4…` 是**另一种算法**，不要混用。）

   配套两件事：
   - **建库写 `embedding_tag`，不一致就自动全量重建**；查询有两道闸门（tag 不符 / 维度不符）
     → 不用向量通道并说明原因。没有这层保护时，换模型后会拿新模型的查询向量去和旧模型的
     存量向量做点积：维度不同变 NaN，维度相同则**完全静默**地给出垃圾排名。
   - **历史缓存键要迁移**：`node tools/migrate-embedding-tag.mjs`（原地 UPDATE 前缀，
     支持 `--dry-run`、可重复执行）。不迁移的话，6.3 万条历史向量会因为前缀不同而全部用不上，
     而它们本来就是同一份模型算出来的。本机实测：一次迁移 63,091 条。

2. **键加盐（HMAC）**（低风险但值得）
   裸 `sha256(chunk 文本)` 意味着：拿到缓存的人可以拿**候选代码**算哈希，
   从而**验证"这段代码在不在公司索引里"**（字典确认攻击）。
   改成 `HMAC-SHA256(salt, 文本)`，盐放在公司内部配置里共享 → 内部照样能合并，
   外部无法枚举。代价同上：键变了要重建。

3. **统一规范键**（见第二节末尾）。

> ⚠️ 这三处都会让**现有 62,479 条缓存作废**。所以**必须一次改完、只重建一次**，
> 不要分成三次改，否则付三遍重建代价。

## 五、体积与算力量级（实测）

- 单条 ≈ **4.2 KB**；当前 62,479 条 = **251 MB**。
- 一个 8,227 块的仓库 ≈ **35 MB**；1,022 块 ≈ 4.3 MB。
- **共享后的总量 = 全体分支的去重并集**，不是各机器相加 —— 分支越相似，越省。
- 冷启动成本（本机实测）：GPU fp16 **47 块/s**、CPU int8 **22 块/s**（5.9 核占用）。
  → 8,227 块 ≈ **3 分钟**（GPU）/ **6 分钟**（CPU）。
- 重建 62k 条 ≈ **22 分钟**（GPU）/ **47 分钟**（CPU），可分批、可断点续跑、
  也可以**由一台机器算一次再发快照**，全组只付一次。

---

## 六、三条必须说清的限制

1. **跨项目几乎无收益**：实测不同项目之间块重合率只有 **0.2%–0.9%**。
   共享只在"**同一仓库的不同分支/版本**"上有效（恰好是你们的场景），
   它**不会**变成"公司级知识库"。别对外承诺超出这个范围的效果。
2. **fp16 与 int8 的向量不可互换**：实测余弦相似 0.955、top-10 重合 58%–80%。
   缓存键已按 tag 分开，所以**不会混**；但全组应**统一量化版本**，
   否则同一份代码在不同机器上的检索质量不一致。
   绝不允许把 int8 的向量喂给按 fp16 建的库。
3. **查询向量没有共享价值**；且**第一个人永远要全量算**，共享只帮后来者。

## 七、同步机制（按你们现状排序）

| 方案 | 评价 |
|---|---|
| **GitLab 产物 + 本地合并** ✅ 推荐 | 你们已有内网 GitLab（`git.example.com`）与 `release/` 产物惯例。一台机器或一个 job 定期带 `max_embed` 跑共享仓库 → 导出快照（可按仓库分片）→ 发成 release 资产 → 其他人 `import` 合并。**纯拉取、无并发写**，最容易落地。 |
| 共享网络盘上直接放 SQLite 让多人写 ❌ | SQLite 在网络文件系统上并发写会损坏数据库。 |
| 小服务（HTTP 查 key）⚪ 备选 | 免去快照分发，但引入运维面（进程、鉴权、可用性），初期不值得。 |

合并实现很简单：`ATTACH` 下载的快照后
`insert or replace into vec(key, dim, v) select key, dim, v from snap.vec`。

## 八、要改的清单与代价

| # | 改动 | 规模 | 主要代价 |
|---|---|---|---|
| 1 | `cache export / import / merge / stats` 工具 | 小 | —（**先做这个就有收益**） |
| 2 | tag 并入模型文件哈希 | 小 | 键变了 → 一次性重建（22–47 分钟，或由快照预热） |
| 3 | 键加盐 HMAC | 小 | 同上（合并到同一次重建） |
| 4 | CDC 分块器（替代固定窗口） | 中 | 键全变 → 又一次重建 |
| 5 | 可选：按仓库分片，避免每人拉全量 | 小 | — |

**建议的落地顺序**：
先做 1（共享本身，不需要动缓存键，立刻可验证收益）
→ 再把 2/3 一起做完并**重建一次**（两处都改键，别分成两次重建）
→ 最后按需做 4（CDC，独立价值是**活跃开发时**减少 2–3 倍重嵌入，与共享无关也该做）
→ 5 按规模决定。
