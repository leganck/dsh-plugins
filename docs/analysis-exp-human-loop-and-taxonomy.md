> 素材：腾讯《AI Coding 的下一站》原文 + 你的 bug-analysis 工作区会话列表
> （正式环境Bug分析插件 / erp需求 / erp bug / 发版准备 / 运营 / 支付 bug / 台账管理 / 本地调试）

## 一、腾讯方案里的人工介入：**链路全自动，人工在链外**

先把一个常见误解纠正掉：**抽取链路本身没有人工关卡**。

```text
对话上报 → 主题分组 → 经验抽取 → Review → Dedup → Merge → 入库 → 召回统计
                                    └────────── 全自动 ──────────┘
```

文章给的数据印证这点：**1,022 条候选 → 三层治理后入库 789 条（77%）**，拦掉的 233 条是规则拦的，
不是人一条条看的。如果靠人审 1,022 条，50 人团队根本跑不起来。

人工介入在 **5 个链外环节**，分"离线建设"与"在线例外"两类：

### 1.1 离线（一次性或周期性，决定链路质量）

| # | 环节 | 人工做什么 | 产出 | 频率 |
|---|---|---|---|---|
| 1 | **垃圾模式标注** | 对候选经验打标（高价值/低价值/垃圾）→ 对垃圾归因 → 归纳模式 | **九类垃圾特征**（事实性错误/通用常识/对话摘要/一次性 case/用户偏好/缺上下文/粒度混用/不可执行/证据不足） | 一次性，后续补 |
| 2 | **评测集构建** | 固定样本 + 人工标注正/负例，防过拟合 | 260 条经验 4 个分组的评测集；六轮 157 样本的 Merge 评测集 | 一次性 + 增量 |
| 3 | **错例分析 → 规则抽象** | 看错例 → 判断误判类型 → 写成可操作规则 → 改 prompt → 重评测 | prompt 迭代 3 轮（整体重构→边界强化→偏好规则硬化） | 每轮迭代 |
| 4 | **指标裁决** | 三指标一起看（Recall / Precision / **Garbage Rate**），决定这版 prompt 要不要上 | 上/不上，以及"哪一层该改"（而不是笼统调参） | 每轮迭代 |

> 文章原话："Prompt 优化要从错例中抽象规则，不是凭感觉改"——这是人工最重的投入，也是唯一能持续改进的地方。

### 1.2 在线（例外通道，必须有但要少）

| # | 环节 | 人工做什么 | 我们的落地 |
|---|---|---|---|
| 5 | **Contradict 人工裁决** | 新旧认知冲突时**不自动放过、不自动决断**，标记后走人工通道 | 已有：经验页冲突卡四键（保留新/保留旧/都保留/**融合**） |

文章对这条给了明确理由：冲突本身是"团队认知变化"的信号，自动压制会丢失信号。

### 1.3 与我们设计的一一对应

| 腾讯环节 | 我们现在的状态 | 缺口 |
|---|---|---|
| 垃圾九类 | ✅ 已写进 prompt 与 Review 规则 | — |
| 评测集 | ✅ 人工 18 正例 + 8 负例（这次做的） | 规模小，需扩到 60+ |
| 错例分析 | ⚠️ 有脚本但没闭环流程 | 需要"错例表"落库 + 迭代记录 |
| Contradict 裁决 | ✅ admin 冲突卡四键 | 缺"裁决理由"留存（现在只存状态） |
| **人工抽检**（文章未强制，但我们要加） | ❌ 无 | 每批每类抽 5 条人工判定，10 分钟/批 |

### 1.4 结论：我们的分工应该是

```text
机器做：抽取 / Review / Dedup / Merge / 入库 / 打点      ← 每条都过，不给人工加负担
人工做：① 定标准（prompt + 九类）② 评效果（gold set + 三指标）
        ③ 裁冲突（contradict）④ 抽检（每批每类 5 条）⑤ 复盘错例
```

**不要设计成"每条经验人工审核"**——那是文档管理，不是经验管道，规模一大必然崩。

## 二、经验类型：三轴模型（结合 8 个工作流）

### 2.1 为什么需要三个轴

| 轴 | 回答的问题 | 取值 | 谁产生 |
|---|---|---|---|
| **lens** | Agent 为什么自己发现不了 | jargon / index / logic | LLM 判定 |
| **category** | 这是哪类知识（决定质量基线与垃圾率） | business / debug / repo / tool / process | LLM 判定 |
| **workflow** | 从哪类工作里长出来的（决定召回场景） | 8 个工作流标签 | **会话名自动带，零成本** |

`workflow` 是白送的：插件已经知道当前会话是哪个（截图里那 8 个），直接作为标签传给抽取端点。
召回时"同工作流经验加权"，比纯语义相似可靠得多——查 erp 线上缺陷时，"发版准备"里的经验通常不相关。

### 2.2 category 五类定义（互斥，可判定）

| category | 定义 | 识别特征 | 反例（不算） |
|---|---|---|---|
| **business** 业务知识 | 业务口径、字段语义、状态机、结算规则、内部黑话映射 | 提到具体业务概念（租户/门店/流水/补录/结余/套餐）且有业务后果 | 只讲代码结构不说业务含义 |
| **debug** 调试经验 | 现象 → 定位手段 → 根因 → 验证方式 | 有"查不到/不对/异常"的现象 + 一个具体定位动作 | 只说"看日志"（不可执行） |
| **repo** 仓库联动 | 跨仓依赖、分支/版本线、构建产物、发布顺序、数据表联动 | 涉及两个以上仓库/分支/版本线，或"改 A 必须同步改 B" | 单仓内的普通实现细节 |
| **tool** 工具环境 | CLI 命令形态、环境变量、平台坑 | 出现命令、参数、环境名、路径改写、超时 | 通用编程常识 |
| **process** 交付流程 | 审批、台账、发版规则 | 出现审批/台账/单号流转 | **默认拒收**（已由 sp-rules / sp-delivery-ledger 等 skill 覆盖） |

**process 拒收不是因为它错**，而是 skill 是"每次进场必读"，经验库是"按需召回"；
同一内容重复放两处，只会稀释经验库的信噪比。

### 2.3 八个工作流的历史记录分析（经验产出画像）

> 下表基于各会话历史内容（erp bug 已逐段细读；其余按会话命名 + 已知台账/交付事实推断，
> 标 ⓘ 的是推断项，P3 评测阶段会用真实抽取结果校准）

| 工作流 | 主要 category 分布 | 真实经验举例（来自历史） | 典型 lens | 召回场景 |
|---|---|---|---|---|
| **erp bug**（23 分钟，主体） | debug 45% / business 35% / tool 15% / repo 5% | 上传流水查不到先比落库分区；pos 表按 posId 查真实归属；store_account 改归属必重算结余；库存扣减写五张表；重放前删 bas_interface_log | logic 为主 | 排查线上 ERP 缺陷、写分析报告前 |
| **支付 bug**（6 小时）ⓘ | debug 50% / business 30% / tool 20% | 上游报文/回包字段比对；svc-pay 状态推进条件；pay 走公共分区 | logic + index | 支付链路取证、对账差异 |
| **发版准备**（2 小时） | repo 45% / process 30% / business 15% / tool 10% | master-5.0.x→5.2.3 禁全分支 merge；merge -s ours 标记已合并；「可摘」黑话；版本线归属判定 | logic + jargon | 建发版分支、移植补丁、出发布计划 |
| **erp 需求**（6 分钟）ⓘ | business 40% / repo 35% / tool 15% / debug 10% | 多仓联动改动清单；开关引用不能传字符串（时机问题导致永远默认关）；区域子树∩机构 | logic + index | 需求实现前确认影响面与联动仓 |
| **运营**（3 小时）ⓘ | business 45% / tool 35% / debug 20% | 销售额/退款口径；devops 查库查日志；租户↔门店↔分区映射 | index + jargon | 运营数据核对、报表口径争议 |
| **台账管理**（1 天）ⓘ | process 50%（拒收）/ tool 30% / repo 20% | ledger 参数形态；facts-check 判据；release-lines 语义 | index | 台账操作（大多已 skill 覆盖） |
| **本地调试**（2 天）ⓘ | tool 70% / repo 20% / debug 10% | Git Bash 用 java 直调 gradle-wrapper.jar；checkstyle 要求 core 排在 crm 前 | index | 本机构建失败、依赖/工具异常 |
| **正式环境Bug分析插件**（5 天，置顶）ⓘ | repo 50% / tool 30% / debug 20% | 插件架构与权限；分析口径与导出格式 | index | 维护该插件本身 |

**从画像能读出的三件事**

1. **erp bug 是最大的经验矿**（debug+business 双高），也是 recall 收益最直接的地方——
   下次拿到一个"XX 查不到"的单子，先召回它就少走两小时。
2. **发版准备与 erp 需求的经验价值不在"怎么做"而在"别怎么做"**（禁全分支 merge、开关不能传字符串）——
   这类"否定式约束"最容易被规则版抽丢，必须靠 logic 镜头专门抓。
3. **台账管理价值密度最低**（process 占一半且被拒收），说明它不是经验矿而是 skill 该管的活——
   这也验证了 process 拒收的合理性。

### 2.4 目标分布（P3 评测后的验收口径）

| category | 目标占比 | 判据 |
|---|---|---|
| debug | 30~35% | erp/支付两类 bug 会话应贡献最多 |
| business | 25~30% | 业务口径与字段语义 |
| repo | 20~25% | 发版/需求/联动的"别怎么做" |
| tool | 12~18% | 命令形态与平台坑 |
| process | **0（全部拒收）** | 拒收计数单独记账，不进垃圾率 |

类型分布若长期偏斜（如 tool 占 60%），说明 prompt 把"好抽的"抽多了，需要按类型加引导。

## 三、LLM 配置放设置页（按你的要求：自己填）

### 3.1 位置与字段

admin 新增 tab **「设置」**（或并入「模型」tab 下的「经验抽取」卡，推荐后者，少一个 tab）：

```text
┌─ 经验抽取 LLM ─────────────────────────────── [测试连通] ─┐
│ 启用              [开/关]                                │
│ Base URL          http://192.168.50.42:13425/v1   ← 自己填 │
│ API Key           ●●●●●●●●●●●●  [显示/替换]              │
│ 模型              auto/deepseek-v4.1-flash               │
│ 单段预算          2000 tokens（输出上限）                 │
│ 超时              60 秒                                   │
│ 日 token 上限     200000（超出当天转 queued，次日续）      │
│ 并发              1（串行，避免限流）                     │
│ ── 最近一次调用：成功 · 1.2s · in 1834 / out 612 · 12:31 ─│
│ ── prompt 版本：exp-v2.3 [查看]（只读）                   │
└──────────────────────────────────────────────────────────┘
```

### 3.2 存储与安全

| 项 | 做法 |
|---|---|
| 存放 | admin.db 的 `settings` 表（与服务已有 ADMIN_PASSWORD 同级；文件权限沿用容器 10001） |
| 展示 | 读取时掩码 `sk-****abcd`；只有"替换"操作能写入 |
| 日志 | 任何日志/异常正文都不打印 Key；`/v1/admin/settings` 响应不含明文 |
| 兜底 | 环境变量 `EXP_LLM_*` 仅在设置页为空时生效（便于容器化部署） |
| 未配置时 | 抽取任务落 `queued` → 标记 `llm-not-configured`，**不报错、不阻塞压缩** |

### 3.3 测试连通按钮

点一下发一个最小请求（`max_tokens=16`，问"回复 OK"），返回三件事：
HTTP 状态 / 耗时 / 模型回显名。**顺便校验"是不是推理型模型"**——若 `content` 为空而 `reasoning_content` 有内容，
直接提示"该模型为推理型，建议换 `*-flash` 或非推理模型"，避免又踩 `glm-5.3` 那个坑。

### 3.4 prompt 版本可见但不可改（重要）

prompt 是质量的核心资产。**页面只显示版本号 + 只读查看**，改动走代码提交（可 review、可回滚、可评测）。
理由：如果允许在页面上随手改 prompt，就回到了文章批评的"凭感觉改"，且无法用评测集衡量收益。

## 四、对原计划的修订（P0 与 P1 调整）

| 原计划 | 修订后 |
|---|---|
| P0：端口转发 + prompt 固化（用 env 配 LLM） | **P0：设置页 LLM 配置（含测试连通）+ 端口转发 + prompt 固化**；配置从 env 改为 UI（env 仅兜底） |
| P1：`category` 列 + exp_jobs + extract 端点 | **P1：加 `workflow` 列**（会话名自动带）+ `audit`（三维）+ `extract_run` + 设置页读写 API + extract 端点 |
| P3：评测 | 追加 **Category Accuracy** 指标（category/workflow 判定与人工标注一致率）+ 类型分布验收（§2.4） |
| P5：admin 呈现 | 追加：经验页按 category/workflow 双维筛选 + 类型分布卡 + 「人工抽检」标记列（抽检过的打勾） |

工期不变（4.5 天），P0 多 0.2 天、P1 多 0.2 天，从 P5 挪。
